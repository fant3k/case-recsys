# Как провести независимое подтверждение

Проверено 21 октября 2026. Это подготовка метода следующей проверки, **не её запуск**. Confirmation и final test не оценивались. Модели и уже полученные результаты не менялись.

## Что подтверждают первичные источники

1. Spotify подчёркивает, что offline model selection не полностью отражает downstream продуктовый результат, и мотивирует рандомизированные онлайн-эксперименты. Демонстрации предложенного метода AOE на этой странице используют симуляторы на letter и MovieLens; это не отчёт о production A/B. Для нашего проекта это граница вывода: offline проверка не является A/B и не доказывает изменение поведения после рекомендации. [Spotify, 2021](https://research.atspotify.com/2021/7/model-selection-for-production-system-via-automated-online-experiments).
2. Работа об adaptive data analysis показывает опасность многократного выбора по одному holdout. Поэтому текущую selection больше не называем независимым подтверждением. Не внедряем сложный reusable holdout задним числом: сохраняем простое одноразовое закрытое окно. [Dwork et al., NeurIPS 2015](https://proceedings.neurips.cc/paper_files/paper/2015/file/bad5f33780c42f2588878a9d07405083-Paper.pdf).
3. Исследование ACM TOIS показывает, что нарушение глобальной временной линии меняет оценки и порядок рекомендателей. У нас остаются общие временные границы, train-only каталог/глобальные признаки и история до запроса. [Ji et al.](https://arxiv.org/abs/2010.11060).
4. Google Research показывает, что sampled ranking metrics могут поменять относительный порядок моделей даже в ожидании. Продолжаем ранжировать весь фиксированный каталог 50 000 треков, без упрощения до правильного трека и случайных negatives. Это не весь каталог сервиса: OOV labels остаются misses. [Krichene & Rendle, KDD 2020](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/).
5. Microsoft рекомендует заранее задавать гипотезу, основные метрики, guardrails и проверки качества данных. Переносим этот принцип на offline опыт. Онлайн-проверки traffic allocation/SRM к нашему парному сравнению одних пользователей не применяются буквально. [Microsoft Research, pre-experiment patterns](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-pre-experiment-stage/).

## Подходящая нам процедура

**Не менять существующие границы protocol v1.** Confirmation query cutoff 25 811 800; labels `[25 813 600, 25 900 000)`. Final query cutoff 25 900 000; labels `[25 901 800, 25 988 200)`. Время — native seconds от неизвестного начала, не календарные даты. Train заканчивается до 25 723 600. Веса, каталог и глобальные статистики не переобучаются.

История пользователя на новом запросе может включать уже прошедшие selection-события — это легитимная доступная история, не обучение на confirmation. Ни одно событие label window не попадает в замороженный дневной query. Для auxiliary next-group применяется прежнее отдельное правило обновлённой strictly-past истории, без изменения основной метрики.

Пользователи остаются теми же: это **не просмотренный период**, а не независимая новая пользовательская выборка. Между днями и пользователями сохраняется зависимость. Одно confirmation-окно не докажет стабильность на всех неделях, новых пользователях или другом сервисе.

Перед чтением новых метрик сохранить manifest: SHA256 policy/RM checkpoints и evaluation code, протокол, seed, список моделей, условия допуска, правила интерпретации. Любая техническая ошибка должна быть описана; после исправления не заменять неудачный результат новым без истории изменений.

### Кого проверять

Предложение для следующего опыта — **один основной кандидат RL cappedseconds β=0,3**, выбранный заранее по уже открытой selection: он даёт понятный небольшой прирост proxy и меньший сдвиг NDCG. Это выбор цели исследования «время при ограниченной потере релевантности», а не утверждение, что он лучше completion во всех смыслах.

Completion β=0,03, формальный кандидат прежнего per-reward selection правила, оставить дополнительным исследовательским сравнением: повтор action-seed дал пограничный результат по relevance. Не выбирать между ними по confirmation и затем называть выбранного независимым победителем. Если решим делать две равноценных подтверждающих гипотезы, правило множественного вывода нужно зафиксировать до запуска; нельзя выдавать две отдельные 95% оценки за одновременную 95% гарантию.

Контроли: исходная reference GPT-2 и сохранённое continued joint SFT, простая частота128, count+recency tie-break, memory50/50. Последняя получает больше истории и остаётся явно помеченной. Checkpoints ровно из завершённой матрицы, без дополнительного подбора LR, β, награды, температуры, веса смеси или выбора seed по confirmation.

### Что считать успехом

Для одного основного кандидата одновременно требуем:

- положительный прирост **предсказанного normalized cappedseconds** по основной RM относительно reference, оценённый на всех warm query users;
- сохранение relevance в ранее заданном допуске5%: нижняя95% граница среднего `NDCG_candidate − 0.95*NDCG_reference` не ниже0 на active-positive пользователях.

Это составной вывод «proxy вырос и релевантность сохранена», а не оптимизация лучшего из нескольких разных показателей. Парные интервалы ресемплируют пользователей с обеими policy-оценками вместе. Для ranking используются только пользователи с положительными day labels; для reward — все warm users независимо от будущей активности. Разница выборок раскрывается.

Показываем также прирост относительно continued SFT, альтернативную RM, Recall/HitRate/Precision, expected versus top10 reward, длительности, repeat/older/new, разнообразие, top-item concentration и KL. Они объясняют результат, но не заменяют основную метрику после просмотра. Новых произвольных порогов для разнообразия по confirmation не придумываем: показываем величину и направление изменения.

Малое число пользователей и редкие попадания могут дать широкий интервал. «Не подтверждено» не равно «эффекта нет»; не увеличиваем допуск5% после неудачи. User bootstrap не измеряет всю неопределённость обучения и не устраняет temporal shift.

### Проверки до метрик

- Точно совпадают пользователи/истины для сравниваемых ranking policy, нет потери неудобных запросов и дубликатов top10.
- Сравнение checkpoint с самим собой даёт нулевую парную разницу; KL допускает только объяснимую численную погрешность.
- Каталог/признаки не используют future, OOV labels не выброшены из ranking denominator, ties не создают утечку.
- Evaluation code и критерии фиксированы до извлечения model scores.

A/A-подобный self-check проверяет реализацию, но не делает offline анализ рандомизированным A/B.

### Что после результата

Если подтверждение не удалось, честно зафиксировать ограничение и не возвращаться к настройке по этому окну. Финальная оценка остаётся для заранее замороженного итогового сравнения; она не должна использоваться для ещё одного выбора модели. Можно получить полезный отрицательный результат задания.

Если будем существенно менять рецепт после confirmation, этот период становится development-данными. Для нового независимого подтверждения нужен ещё неиспользованный период или новая выборка; нельзя переименовать уже просмотренное окно в «независимое».

## Какие дополнительные приёмы нужны сейчас

**Нужны:** заранее зафиксированные primary/guardrail критерии, manifest с hash, self-comparison, парные интервалы, полный каталог, сильные простые контроли, единый отчёт с отрицательными результатами. Большинство уже реализовано в текущей матрице; осталось применить их к закрытому окну без подбора.

**Полезны отдельно:** повтор основного RL-рецепта с ещё одним заранее заданным seed до открытия confirmation, с отчётом обо всех seeds без выбора лучшего. Один повтор не заменит набор независимых периодов. Если сравнивать разные seeds, должны быть заранее определены и сопоставимые SFT-контроли, а не победитель после просмотра.

**Сейчас не нужны:** новая архитектура, новый набор функций, случайный k-fold вместо временной проверки, сложные online bandits, CUPED без настоящей рандомизации, IPS с придуманными propensities и искусственные «пользователи», выдаваемые за реальную проверку. Эти техники не создадут недостающую обратную связь из наших логов.

Следующий конкретный шаг — подготовить зафиксированный evaluation manifest и один раз оценить основной кандидат на confirmation. В рамках данного поиска этот шаг ещё не выполнялся.
