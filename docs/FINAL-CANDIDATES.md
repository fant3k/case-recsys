# Финальный тест: зафиксированные кандидаты и критерии

Зафиксировано 23 октября 2026 **до** чтения событий и меток финального окна. Окно final test ни разу не оценивалось. Код оценки — `recsys/final_test.py`; при запуске он записывает SHA256 этого документа, протокола, кода и всех checkpoints в `locked-manifest.json` **до** загрузки событий. После открытия финального окна ничего здесь не меняется, кандидаты не добавляются и не подбираются; повторного финального прогона нет.

## Окно

Протокол `research/protocol/case2-v1.json`: срез запросов `final_test` = 25 900 000, метки — уникальные пары пользователь–трек с played_ratio_pct > 50 в [25 901 800; 25 988 200) (зазор 1800 с, горизонт 86 400 с). Максимальный timestamp данных 26 000 000 — окно внутри данных. История запроса — все события строго до среза, последние 128 для политик; веса и каталог заморожены на train end 25 723 600, ни одна модель на событиях после train end не обучалась.

Ранжирование: макро NDCG@10 среди warm-пользователей с хотя бы одной будущей положительной парой (условно на активности); полный каталог 50 000; треки вне каталога — промахи. Ожидаемая награда — все warm-пользователи на срезе.

## Почему такие кандидаты

Окно selection использовано для десятков политик, confirmation — для другого кандидата (RL capped seconds из первой цепочки; сохранение релевантности там не подтвердилось). Поэтому финальное окно — единственная чистая проверка. Проверяются **две** гипотезы — по одной на каждый главный вывод исследования, с поправкой на множественность.

## Подтверждающие гипотезы

Общие для обеих: опорная политика `reference` — GPT-2 + PPS + отклик во входе (`artifacts/pps-20261022-01/full+pps+fb-d0.1-wd0.01/last.pt`, на selection NDCG@10 0,1473). Модель награды — RM v2 (`artifacts/reward-v2-20261022-01`): proxy — среднее seeds 0 и 1, судья — seed 2, ни в одной цели не участвовал. Парный bootstrap по пользователям, 10 000 повторов, seed 20261025. Поправка Бонферрони на 2 гипотезы: каждый интервал двусторонний **97,5%** (квантили 1,25% и 98,75%).

### H1. Перевзвешивание топ-50 моделью награды при выдаче повышает релевантность

Кандидат `A_rm_rerank_top50`: π_A ∝ π_ref · exp(r/β), β = 0,03, где r — proxy-прогноз доли дослушивания для 50 треков с наибольшей вероятностью π_ref; остальные треки получают взвешенное по π_ref среднее этих 50 (их относительная масса не меняется). Выдача — топ-10 π_A. Это аналитический оптимум KL-регуляризованной цели RL, вычисленный при выдаче, без обучения весов. На selection: NDCG@10 0,1585 (+7,6%), награда +2,3% / +1,9% (RL v3).

**Критерий:** нижняя граница 97,5% интервала mean(NDCG_A − NDCG_ref) > 0.

### H2. Обученная RL-политика повышает предсказанные секунды без потери релевантности больше 5%

Кандидат `B_rl_seconds_beta0.3`: RL v2, награда capped seconds (прогноз доли × min(медианная длина, 600)/600), β = 0,3, фиксированный последний шаг (`artifacts/rl-v2-20261023-01/rl_seconds_beta0.3.pt`). На selection: секунды +6,7% по proxy и по судье, NDCG −0,6%.

**Критерий (оба условия):**
1. нижняя граница 97,5% интервала разницы ожидаемых capped seconds **по судье** (seed 2), B − reference, по всем warm-пользователям > 0. В отчёте награда умножена на 600 и выражена в эквивалентных секундах (прогноз доли × min(медианная длина, 600) с); на знак и решение множитель не влияет;
2. нижняя граница 97,5% интервала mean(NDCG_B − 0,95·NDCG_ref) ≥ 0.

Оба условия — внутри одной гипотезы (intersection-union), отдельной поправки не требуют.

### Как формулировать итог

- Нижняя граница выше порога — «подтверждено на финальном окне» для этой офлайн-гипотезы. Это не доказательство пользы для реальных пользователей: награда — прогноз RM, NDCG — совпадение с залогированными прослушиваниями, когорта та же, день более поздний, не online A/B.
- Не прошло — «не подтверждено». Это не доказывает обратного эффекта; приводить точечную оценку и интервал.
- Proxy-награду, доли дослушивания и описательные сравнения приводить, но решений по ним не принимать.

## Проверки корректности в том же запуске

- Сравнение reference с самим собой даёт разницу 0 и интервал [0; 0]; KL reference к себе 0.
- Хэши всех checkpoints после оценки совпадают с записанными в манифесте; веса заморожены, градиентов нет.
- Пользователи в парных сравнениях совпадают поштучно.

До открытия финального окна тот же код один раз прогоняется в режиме `--window selection` на уже использованном окне selection. Он должен воспроизвести известные значения (reference 0,1473, A 0,1585, B 0,1464, частота 0,1805, память 0,1958, реранкер 0,2349). По этому прогону ничего не выбирается и не меняется в критериях; если значения не совпадают, ищется ошибка в коде оценки.

## Чего этот тест не покажет

Один период и одна когорта 1000 пользователей Yambda; bootstrap не учитывает неопределённость обучения (один seed на модель) и сдвиг во времени. Судья обучен на тех же логах, что и proxy. Ни NDCG, ни прогноз награды не являются причинной пользой для пользователя.

## Исправления после ревью (до открытия final)

Внешнее ревью — [FINAL-TEST-REVIEW-2026-10-23](FINAL-TEST-REVIEW-2026-10-23.md). Утечек и нарушения парности в H1/H2 оно не нашло, нашло четыре несоответствия и одну незакрытую проверку. Все исправлены до открытия финального окна; кандидаты, пороги, уровень 97,5% и правила решений **не менялись**.

1. **Единицы.** Поля «секунды» содержали нормированную награду протокола (доля × min(длина, 600)/600). Теперь в отчёте `*_equivalent_seconds` = эта величина × 600; поле топ-10 переименовано в `mean_capped_length_seconds`. Обучающая награда и β политики B не менялись.
2. **Реранкер.** Общие статистики треков пересчитывались по всем событиям до среза, включая события после конца train, — протокол это запрещает для подогнанных статистик. Теперь они заморожены на конце train (`reranker.build(..., stats_cutoff=train_end)`); личные признаки пользователя по-прежнему из истории до среза, это протокол разрешает. На selection срез совпадает с концом train, поэтому значение 0,234869 не изменилось. Реранкер — описательная строка, в H1/H2 не участвует.
3. **PairAccuracy.** Метки во float32: 0,7 − 0,2 = 0,49999998 < 0,5, и пары ровно на границе 50 п.п. выпадали. Теперь порог сравнивается с допуском 1e-6 (`reward_v2.LABEL_TOLERANCE`), тест на 50 и 49 п.п. Это меняет только описательную PairAccuracy; ранее опубликованные значения PairAccuracy в отчётах RM v2 и RL посчитаны старым правилом и не пересчитывались (на selection разница: 204 694 → 205 529 пар, macro у reference 0,53080 → 0,53088).
4. **Однократность.** `--out` для финального окна запрещён, выход только `artifacts/final-test-20261023-01`. До создания папки и загрузки событий атомарно создаётся маркер `artifacts/FINAL-TEST-OPENED.json` (O_CREAT|O_EXCL); при его наличии запуск отказывает, маркер остаётся и после ошибки. Проверено тестами на временном каталоге; настоящий маркер не создавался.
5. **Причина расхождения A подтверждена.** `artifacts/a-precision-check-20261023-01` (код `recsys/a_precision_check.py`, selection, 16 с): тот же top-50 и β, награда из FP16-кэша полного каталога даёт NDCG 0,1585161815 — ровно значение RL v3; прямой расчёт в FP32 даёт 0,1582555762 — ровно значение пробного прогона. Максимальная разница наград 0,00024, средняя 0,00007; из-за усиления r/β (×33) у 125 из 1000 пользователей меняется порядок топ-10, у 26 — состав. **Зафиксированная реализация A — FP32** (точнее). Вывод для отчёта: выдача A чувствительна к разницам наград порядка 1e-4 при β = 0,03.

Повторный пробный прогон с исправлениями — `artifacts/final-dryrun-selection-20261023-02`, 33 с, 76 тестов на Windows прошли перед ним, самосравнение и хэши PASS, `final_test_scored` false. Все NDCG совпали с первым прогоном до шестого знака. На selection (окно использовано многократно, это не подтверждение): H1 ΔNDCG +0,0110 [97,5%: +0,0048; +0,0176]; H2 секунды судьи +9,24 с [+8,48; +10,10], запас mean(NDCG_B − 0,95·NDCG_ref) +0,0065 [+0,0026; +0,0103].

Ограничения, на которых настаивает ревью и которые войдут в отчёт: судья обучен на тех же логах и на родственной основе — это другой замороженный прогноз, не независимая истина; кандидаты выбраны после многократного использования selection; допуск 5% взят из исходного протокола; H1 — перевзвешивание при выдаче без изменения весов.
