# Обучение GPT-2 на всех позициях: результат

Окно selection (492 пользователя), использованное многократно, — исследовательская оценка. Confirmation и final test не оценивались.

## Выводы

1. Прежняя GPT-2 была недообучена: тот же рецепт с одной целью за 25 минут даёт 0,094 вместо 0,060 и ещё растёт.
2. Обучение на всех позициях даёт ещё +0,032 и выходит на плато уже за 5 минут.
3. У `full` train loss падает до 4,5, а validation NLL стоит на 7,66–7,68: модель переобучается на 1000 пользователях. Следующее ограничение — объём данных и регуляризация, а не время обучения.
4. Разрыв с частотой сократился с ~0,12 до ~0,054, но остаётся значимым; повторы недавних треков всё ещё недоиспользуются (360 против 669).

Один seed; лучший checkpoint выбран на том же окне. Артефакты: Windows `E:\Projects\Debug\artifacts\fullsft-20261022-01` (`{last,full}/best.pt`, `evaluations.json`, `report.json`), копия report на Mac.

Целей на шаг: 6 320 и 11 743. Пик памяти 2,13 и 2,14 ГиБ из 12.

По ядрам GPU (full, на шаг): матричные умножения ~42 мс (~28%); log_softmax прямой ~28 мс, его обратный ~14 мс, приведения fp16→fp32 (`copy_`) ~26 мс, прочие поэлементные ~26 мс — вместе ~94 мс (~60%). Профайлер показывает одно и то же время и для оператора, и для его ядра, поэтому строки в report.json нельзя просто складывать.

- GPU занят практически весь шаг; CPU — меньше 4%. Предрасчёт дневных целей сэкономил бы не больше ~2%.
- Основное время — не вычисления, а поэлементная работа softmax/CE в fp32 по 50 тыс. трекам: ограничение по пропускной способности памяти.
- Видеопамять загружена на ~18%.

## PPS и отклик во входе, `pps-20261022-01`

Лесенка из четырёх вариантов с нуля, по 600 с обучения, dropout 0,1, weight decay 0,01, одинаковые начальные веса и контексты. 48 тестов прошли, пропусков GradScaler нет. `+pps` — фиксированный приоритет ln(1+c/0,01) к логитам при обучении и оценке (Abbattista et al., RecSys 2024); `+fb` — во входе корзины доли прослушивания и log2-интервала до предыдущего события; `+pos` — только цели с долей >50%.

| Обучение, с | full | +pps | +pps+fb | +pps+fb+pos |
|---:|---:|---:|---:|---:|
| 0 | 0,0186 | **0,1721** | **0,1726** | **0,1726** |
| 150 | 0,1044 | 0,1552 | 0,1557 | 0,1559 |
| 300 | 0,1174 | 0,1464 | 0,1485 | 0,1443 |
| 450 | 0,1311 | 0,1418 | 0,1449 | 0,1394 |
| 600 | **0,1316** | 0,1423 | 0,1473 | 0,1394 |
| val NLL на 600 с | 7,50 | 8,18 | 8,13 | 8,33 |

PersonalFrequency128 — 0,1805. Шагов за 600 с: 4157 / 2863 / 2856 / 3933.

- У всех PPS-вариантов лучший NDCG — на шаге 0, то есть случайный трансформер плюс счётчики: по сути частота с другим разрешением равенств (0,172 против 0,1805). Обучение только снижает NDCG.
- Интервалы «PPS − контроль» в report.json (+0,040…+0,041) относятся к этим checkpoint шага 0, а не к обученным моделям. На 600 с обученные PPS-модели выше контроля на 0,008–0,016 (интервал для них не считался).
- Validation NLL следующего трека у PPS хуже контроля (8,13–8,33 против 7,50): при ε=0,01 приоритет повторов слишком силён для задачи «следующий трек», и обучение тратит ёмкость на то, чтобы его гасить. Для дневной метрики этот же приоритет почти оптимален. Две цели требуют разной силы повторов.
- Отклик во входе: +0,005 на 600 с (0,1473 против 0,1423), один seed, без интервала. Цели только >50%: хуже (0,1394).

Вывод: на этой метрике обучение следующему треку не улучшает частотный приоритет, даже когда он встроен. Следующая проверка — дневная цель поверх PPS. Один seed, selection использован многократно; confirmation и final test не оценивались.
